# מערכת הניהול של החוג של הניה טייכטל

React + Vite + TypeScript · Supabase (Postgres, Auth, Edge Functions) · Tailwind RTL

## הפעלה ראשונה

```bash
npm install
cp .env.example .env.local     # מלאי URL ו-anon key מהפרויקט ב-Supabase
npm run dev
```

`.env.local` ב-`.gitignore`. **מפתח `service_role` לעולם לא נכנס לריפו ולעולם לא לפרונט** —
הוא נקבע כסוד של Edge Functions בלבד:

```bash
supabase secrets set SUPABASE_SERVICE_ROLE_KEY=...
```

## מסד הנתונים

כל שינוי סכמה עובר במיגרציה תחת `supabase/migrations/`. **אין עריכה ידנית בדשבורד של Supabase.**

```bash
supabase link --project-ref <ref>
supabase db push               # מחיל מיגרציות על הפרויקט המרוחק
npm run db:reset               # מקומי: בונה מאפס + seed + משתמשים
```

**משתמשים לא נוצרים ב-SQL ולא בסקריפט.** חשבון נוצר רק בכניסה בגוגל של
אימייל שברשימת המורשים (`allowed_users`). `seed.sql` מכיל נתונים עסקיים
בלבד; `seed_allowlist.sql` מכיל את הבעלים הראשונה ורץ בכל פריסה. ראה
"כניסה והרשאות" למטה.

| קובץ | תוכן |
|---|---|
| `supabase/migrations/0001_init.sql` | enums, טבלאות, אינדקסים, views, `f_general_allocation` |
| `supabase/migrations/0002_rls.sql` | RLS על כל טבלה, פוליסות, תצוגת רואת חשבון |
| `supabase/migrations/0003_allocation_largest_remainder.sql` | חלוקת הוצאות בשיטת השארית הגדולה |
| `supabase/migrations/0014_google_allowlist.sql` | רשימת המורשים, השער על `auth.users`, סנכרון תפקידים |
| `supabase/migrations/0015_productions_reports.sql` | תצוגות הדוחות: רווח לפי הפקה, רווח והפסד חודשי, רווחיות סניפים, המרת פניות |
| `supabase/seed.sql` | עונה, 5 סניפים, 21 תלמידות, תשלומים, כספים, הפקות, נוכחות, תבניות, הגדרות |
| `supabase/seed_allowlist.sql` | הבעלים הראשונה ברשימת המורשים. אידמפוטנטי, רץ בכל פריסה |

### אימות בלי Supabase חי

הריפו מריץ את כל הסכמה על פוסטגרס מקומי, כדי שאפשר יהיה לאמת בלי לחכות למפתחות:

```bash
npm run db:reset:local     # בונה מאפס: shim + מיגרציות + seed + משתמשי בדיקה
npm run db:test            # הוכחת RLS + הוכחת חלוקת הוצאות
npm run db:test:negative   # בקרת שלילה: פותח כל חור ומוודא שהחבילה נופלת
```

`supabase/tests/00_local_auth_shim.sql` מחקה את סכמת `auth` של Supabase, ו-`01_local_users.sql`
יוצר שלוש זהויות בדיקה דרך אותו שער שעוברת כניסה אמיתית (שורה ברשימה, ואז
שורה ב-`auth.users` עם ספק google — הפרופיל נוצר בטריגר). שניהם **לא**
מיגרציות ולא רצים בפרודקשן. המקבילה לענן: `npm run seed:identities`.

## הוכחת ה-RLS

`02_rls_proof.sql` מריץ שאילתות ישירות בתור `authenticated` עם JWT claims אמיתיים —
בדיוק כמו supabase-js — ומוודא שההפרדה בין הסניפים נאכפת **במסד**, לא בפילטר בצד הלקוח.
כולל קטגוריית הסלמת הרשאות: ניסיון של מנהלת סניף להפוך את עצמה ל-owner, לשייך את עצמה
לסניף אחר, או להוסיף מספר מורשה לפקודות וואטסאפ.

`03_allocation_proof.sql` מוודא ש-`sum(allocated) = amount` בדיוק, לכל שיטות החלוקה
ולכל סכום, כולל 12,000 ש"ח לשבעה סניפים.

`negative-control.sh` פותח כל חור בנפרד ומוודא שהחבילה נופלת עליו. בדיקה שתמיד עוברת
אינה מוכיחה דבר.

## עמידות בנתונים אמיתיים

מה נקבע אחרי סבב הנתונים (0020, `14_real_data.sql`):
- **תשלום נושא את הסניף שבו נרשם.** תלמידה שעברה סניף: ההיסטוריה נשארת
  בסניף הישן, רק תשלומים חדשים נספרים בחדש. היתרה שלה עצמה כוללת הכל.
- **הוצאה כללית "לפי תלמידות" כשאין תלמידות פעילות** (חופשה) מתחלקת שווה
  במקום להיעלם מרווחיות הסניפים.
- **סגירת סניף** — כפתור לבעלים במסך הסניף (הגדרות), דרך `rpc_close_branch`:
  רק כשאין תלמידות פעילות/ממתינות; ההיסטוריה נשארת, קישור הנוכחות מתבטל.
  מחיקה קשה נחסמת במסד.
- **תשלום יתר / תשלום ביתרה אפס** מתקבל (זכות), עם אזהרה בטופס.
- **חייבת בלי טלפון**: תג "אין טלפון" בגבייה, והתראה יומית לבעלים מ-`cron-debt`.


`14_real_data.sql` (מקומי, רץ ב-`run.sh`): תלמידה בלי הורה/טלפון/סכום, סניף
ריק ותלמידה שעברה סניף, תשלום יתר ותשלום ביתרה אפס, מחיקת סניף עם
תלמידות (נחסמת במפתח זר; מחיקה רכה משאירה את התלמידות ברשימה), שמות של
350+ תווים עם גרשיים/מקף עברי/מירכאות, ו-500 תלמידות + 3,000 תשלומים +
10,000 סימוני נוכחות עם תקרת זמן לכל מסך (הכבד ביותר, מסך התלמידות: ~0.4
שנ' מקומית). תרגיל השחזור: [docs/RESTORE.md](docs/RESTORE.md).

## בדיקות אבטחה — כלל מחייב

**בדיקת אבטחה מוכיחה את ההרשאה או את המצב, לא את קוד השגיאה.**

הכלל הזה נלמד פעמיים, בשני סבבים שונים, כששתי סיבות שונות החזירו
SQLSTATE זהה ובדיקה דיווחה ✓ בטעות:

| הבדיקה | מה חשבנו שהיא בודקת | מה באמת קרה |
|---|---|---|
| מנהלת משנה את התפקיד שלה ל-owner | RLS חוסם | `permission denied for schema auth` — פגם ב-shim |
| anon חסום מ-`students` | אין GRANT | `permission denied for function my_branches` |

שתיהן `42501`. בדיקה שתפסה `insufficient_privilege` עברה בשני המקרים.

הצורות המותרות, ב-`supabase/tests/_assert.sql`:

* `assert_no_effect(label, action, probe)` — מריץ את הפעולה האסורה, בולע
  כל שגיאה, ומוכיח ש**המצב לא השתנה**. לא משנה למה היא נחסמה; משנה
  שהיא לא קרתה. המסר מדווח גם *איך* נחסם (`נחסם (42501)` או `ללא שגיאה`).
* `assert_no_table_privilege(role, tables[])` — ברמת ה-GRANT, על ארבע
  הפעולות. grant שנוסף בטעות נתפס גם אם RLS במקרה מסתיר את השורות.
* `assert_no_execute(role, signature)` — הרשאת הרצה על פונקציה.

`grep "exception when insufficient_privilege" supabase/tests/*.sql` חייב
לחזור ריק.

## כיסוי פונקציות — כלל מחייב

**בדיקה שרק מוודאת חסימה אינה מוודאת שהדבר עובד.**

`rpc_issue_attendance_link` הייתה מכוסה בבדיקה שמוודאת ש-anon חסום ממנה,
ותו לא. באג שהפיל אותה לגמרי בענן שרד 374 בדיקות, כי אף אחת לא הריצה
אותה. `npm run test:coverage` נכשל על פונקציה שאין לה קריאה חיובית באף
חבילה — טריגרים נספרים דרך הבדיקה שמפעילה אותם.

## ניידות לענן — כלל מחייב

`10_portability_proof.sql` תופס הנחות שנכונות מקומית ולא בסופבייס:

* פונקציה עם `search_path` נעול שקוראת לפונקציה מסכמת `extensions`
* הרחבה שמותקנת ב-`public` (ואז ה-shim מסתיר כשלים במקום לחשוף)
* פונקציה `security definer` בלי `search_path` נעול
* הרשאות ש-`alter default privileges` מעניקה אוטומטית ל-`anon`
* פונקציה שנפתחה ל-`anon` מעבר לשתיים של דף הנוכחות
* קוד שקורא מ-`auth.users`, שה-shim מספק ממנה גרסה מפושטת

## עקביות דוחות כספיים — כלל מחייב

`05_role_consistency_proof.sql` מוודא שכל דוח כספי מחזיר **אותם מספרים** לבעלים
ולרואת חשבון. אם השניים רואים מספרים שונים לאותו דוח — זה באג בהגדרה.

שני באגים אמיתיים נתפסו כך:

| מה | מה רואת החשבון ראתה | מה שהיה נכון |
|---|---|---|
| חלוקת הוצאות כלליות | 8,400 | 12,000 |
| הכנסות מתלמידות | 0 | 20,700 |
| חוב פתוח | 0 | 20,600 |

שניהם מאותו שורש: **דוח כספי שנשען על RLS של טבלה שמכילה מידע אישי.**
לרואת חשבון אין גישה ל-`students` בכוונה, ולכן כל דוח שקורא ממנה דרך
`security_invoker` החזיר לה אפסים — לא חסרים, אלא שגויים ומוצגים כנכונים.

**הכלל:** דוח כספי לא נשען על RLS של טבלה עם מידע אישי. הסינון נכתב במפורש
בתצוגה, והמידע האישי ממוסך לפי תפקיד (`v_debtors.parent_phone` מוחזר `null`
לרואת חשבון — אותם סכומים, בלי טלפונים).

**כל דוח כספי חדש מקבל שורה בקובץ הזה.** גם דוחות הסבבים הבאים —
רווח והפסד, נשירה, רווח לפי הפקה, המרת פניות.

הבדיקה מוגנת מפני עצמה: `p_min_owner` מוודא שהבעלים מקבל ערך משמעותי,
כדי שהשוואה בין שני אפסים לא תיחשב הצלחה. בקרת שלילה מרוקנת את
`payments` ומוודאת שהבדיקה נופלת ולא עוברת.

## כניסה והרשאות — מודל הזמנות בלבד

**יציאה אוטומטית.** 30 דקות בלי פעילות → יציאה, עם אזהרה וספירה לאחור דקה
לפני (כדי לא לאבד הזנה באמצע). מבוסס על חותמות זמן: מחשב שנרדם מתנתק
בחזרה. מסך האחראית (`/a/:token`) אינו כפוף — אין בו מידע רגיש. החלפת
משתמשת באותו טאב (כולל יציאה) מנקה את כל מה שנטען לזיכרון.
`src/lib/idle.ts`, `idle-logout.test.mjs`.


**גוגל בלבד. אין אימייל וסיסמה, לא במסך ולא במערכת.** ספק האימייל של
GoTrue כבוי, ואף קריאת `signInWithPassword` לא קיימת בקוד (נאכף ב-
`public-surface.test.mjs`).

**רק אימייל שברשימת המורשים נכנס.** הרשימה היא הטבלה `allowed_users`.
החסימה אינה במסך: טריגר על `auth.users` (`f_auth_user_gate`) מפיל את
יצירת החשבון עצמה לאימייל שאינו ברשימה, או שאינו מגיע מגוגל. מי שנדחתה
לא מקבלת שורה ב-`auth.users`, ולכן אין לה JWT ואין לה מה להראות ל-RLS.
היא רואה מסך "אין לך הרשאה", ולא נוצר לה חשבון.

שלוש שכבות, כל אחת עומדת לבדה (`11_allowlist_proof.sql`):

| שכבה | מה היא עושה | הבדיקה |
|---|---|---|
| טריגר על `auth.users` | לא ברשימה / לא גוגל / מושבתת → אין חשבון | הוספה ישירה ל-`auth.users` נחסמת, המצב לא משתנה |
| `profiles` + `auth_role()` | פרופיל נוצר רק בטריגר; תפקיד מוחזר רק לפרופיל פעיל | JWT תקין בלי פרופיל: אפס שורות **בכל** טבלה ב-public, בלולאה |
| `allowed_users` → סנכרון | תפקיד, סניף, השבתה והסרה נאכפים בטריגר | שינוי ברשימה משתקף בפרופיל וב-`branch_staff`; מושבתת רואה כלום |

בקרת השלילה פותחת כל אחת מהן בנפרד (הסרת הטריגר, `auth_role` שמתעלמת
מהשבתה, ניתוק הסנכרון, פתיחת הרשימה לכל מחובר, נעילת הבעלים האחרונה)
ומוודאת שהחבילה נופלת. מול הענן, שלב 3 (`verify-access.mjs`) מריץ את
אותו דבר דרך ה-Admin API — שמוסיף ל-`auth.users` בדיוק כמו GoTrue אחרי
גוגל ועובר באותו טריגר.

### מסך המשתמשים (הבעלים בלבד)

`/users`. הבעלים רואה את כל המורשות, מזמינה לפי אימייל, קובעת תפקיד
(בעלים / מנהלת סניף / רואת חשבון), משייכת מנהלת לסניף, משביתה או מסירה.
המסך כותב רק ל-`allowed_users`; כל השאר נגזר בטריגרים. הבעלים הפעילה
האחרונה שכבר נכנסה אינה ניתנת להשבתה או להסרה — אחרת אין מי שיזמין.

**ממתינה:** מוזמנת שטרם נכנסה מופיעה כ"ממתינה" והתפקיד שלה מחכה לה.
בכניסה הראשונה בגוגל עם אותו אימייל היא מקבלת אותו אוטומטית.

### ⚠️ הוספת משתמשת דורשת שתי פעולות

1. **הזמנה במערכת** — מסך המשתמשים.
2. **הוספה כ-test user בגוגל** — Google Cloud ← APIs & Services ←
   OAuth consent screen ← Test users ← Add users.

אפליקציית הגוגל של המערכת נמצאת במצב Testing (פרסום דורש קישורי מדיניות
פרטיות ותנאי שימוש). במצב הזה גוגל מכניס רק אימיילים שנוספו שם ידנית,
עד 100. **אם שוכחים את הפעולה השנייה, גוגל חוסם את המוזמנת עוד לפני
שהמערכת רואה אותה** — היא תראה שגיאה של גוגל, לא את מסך "אין לך הרשאה".

### הבעלים הראשונה

`supabase/seed_allowlist.sql`. אידמפוטנטי: רץ בכל פריסה ובכל סבב אימות,
ומוודא שהיא עדיין בעלים ופעילה. השם נלקח מחשבון הגוגל בכניסה הראשונה.

### זהויות הבדיקה

שלוש זהויות (`@teichtal.local`, בעלים / מנהלת ביתר עילית / רואת חשבון)
קיימות כדי שחבילות ה-SQL ירוצו בשלושת התפקידים. מקומית:
`01_local_users.sql`. בענן: `npm run seed:identities` מריץ **את אותו קובץ**
דרך ה-Management API (או `PGURL`), כלומר אותו שער. לא דרך ה-Admin API:
הוא מוסיף ל-`auth.users` עם ספק email ורק אחר כך מעדכן, והטריגר דוחה
אותו — כמו שהוא אמור. אין להן סיסמה ואין להן חשבון גוגל, ולכן **אי אפשר

## סוכן הלקוחות (סבב 7)

`/agent`, הבעלים בלבד: סימולטור, שיחות, מאגר שאלות, **מידע על החוג**,
שאלות ללא מענה, ומתג "רשאי לנקוב במחירים" (`settings.agent_may_quote_prices`).

**מידע על החוג** (`knowledge_sections`, 0021): בסיס ידע חופשי, כמו מסמך,
מחולק לקטעים עם כותרת. הסוכן מקבל אותו כהקשר בכל תשובה, ביחד עם המאגר.
סדר העדיפות נאכף ב-`_shared/answer-resolve.ts`, בקוד ולא בפרומפט:
1. שאלה תואמת במאגר → התשובה של הניה **מילה במילה**. המאגר גובר.
2. אחרת → מהמידע על החוג, ורק כשהמודל הצביע על קטע קיים (כותרת). בלי
   עיגון זו המצאה → אין תשובה.
3. אין בשניהם → המשפט הקבוע והעברה לבעלים.
על תשובה מהמידע חלים גם: `quotesPrice` (כשהמתג כבוי) ו-`promisesPlaceOrDiscount`
(מקום/הנחה). הסימולטור מסמן מאיפה הגיעה כל תשובה ומה נחסם.

המסלול האמיתי: `wa-webhook` ← הנתב מזהה מספר שאינו מורשה ← `_shared/customer.ts`
← הספק ב-`_shared/answer.ts` (Claude, או פלטים מוקלטים ב-`AI_DRY_RUN`) ←
`deliverReply`. התשובה נרשמת כהודעה יוצאת, וזו ההיסטוריה שהסוכן רואה
בהודעה הבאה ומסך השיחות מציג.

| כלל מהאפיון | איפה נאכף | הבדיקה |
|---|---|---|
| עונה רק מהמאגר | הפרומפט, ו-`no_answer` מקבל תמיד את המשפט הקבוע (`answer-schema.ts`) | שאלה זרה מחזירה את המשפט מילה במילה |
| שאלה ללא תשובה נרשמת ומתריעה | `customer.ts` | שורה ב-`unanswered_questions` + התראה עם הטלפון והשאלה |
| **לא נוקב במחירים** | `quotesPrice()` בקוד, לא בפרומפט. מודל שנקב — ההודעה מוחלפת בהפניה | פלט מוקלט שנוקב מחיר, גם דרך המידע החופשי, לא מגיע להורה; עם המתג דולק — עובר |
| המאגר גובר על המידע החופשי | `resolveAnswer`: התאמה במאגר → התשובה מהמאגר מילה במילה | פלט שמנסח מחדש שאלה שבמאגר — יוצאת התשובה של הניה |
| תשובה חופשית רק מעוגנת | `resolveAnswer`: כותרת קטע קיימת, אחרת `ungrounded` → הפניה + התראה | כותרת שלא קיימת ("סניפים בצפון") לא יוצאת |
| לא מבטיח מקום או הנחה | `promisesPlaceOrDiscount()` בקוד | "שמרתי לך מקום ויש הנחה" מוחלף בהפניה + התראה |
| הרשמה → תלמידה ממתינה | `customer.ts`: רק כשכל חמשת הפרטים ידועים והסניף קיים | `status='pending'`, `source='whatsapp'`, שכר לימוד של הסניף, שיחה מקושרת, התראה "ליד חדש" |
| השתלטות אנושית | `conversations.is_human_takeover` | אפס כתיבות, אפס מענה |
| פלט פגום לא מגיע להורה | `validateAnswer` | JSON שבור, kind לא חוקי, תשובה ארוכה מדי → הפניה |

`customer-agent.test.mjs` מריץ את כל זה מול מסד מזויף שמתעד כל כתיבה
וספק וואטסאפ מזויף שמתעד כל שליחה, בלי מפתח. שש בקרות שלילה פותחות
כל כלל בנפרד (שומר המחירים, השתלטות, רישום שאלה, ליד לא שלם, פלט פגום,
ניתוק הניתוב) ומוודאות שהבדיקה נופלת.

**הכל ב-`AI_DRY_RUN=true`.** החיבור האמיתי למודל מחכה למפתח. `ai-answer`
(הסימולטור) היא פונקציה טהורה כמו `ai-command`: בלי לקוח מסד, ההקשר
מגיע מהקוראת. `ai-command-purity.test.mjs` אוכף את זה על שתיהן.

## הרשמה לחוגים — "דרמחול - החוגים של הניה"

**דף ציבורי** `/enroll` (מחוץ לשער, כמו `/pay`): שם פרטי ומשפחה, כיתה, בית ספר,

הכל מהמסד (`rpc_enrollment_public`): שם החוג, התקנון ומבנה התשלום נערכים
ב**הגדרות → הרשמה לחוג**, בלי קוד. `rpc_enroll` (anon) מאמת שדות, מגביל קצב
(3 בשעה מטלפון, 10 מ-IP, 40 בסך הכל → התראה), מסנן כפילויות, ויוצר:
תלמידה **ממתינה** (`source='enrollment'`, מבנה התשלום מוחל, `terms_accepted_at`,
`trial_started_on`) + **קישור תשלום על החיוב הראשון** (אותו מנגנון SUMIT,
`payment_links.purpose='enrollment'`) שמוצג מיד וגם נשלח בוואטסאפ. שדות זרים
בבקשה (סכום, סטטוס) מתעלמים — 17 מוכיחה.

**מבנה התשלום** (`settings.enrollment_plan`): 1,200 = 100 דמי רישום + 10 × 110.
`f_enrollment_plan()` מסרבת אם לא מסתכם בדיוק, ואז גם ההרשמה מסרבת ומסך
ההגדרות מראה אדום. דמי הרישום הם עמודה נפרדת (`students.registration_fee`),
נכנסים ליתרה, ומופרדים בדוחות (`v_student_balance.registration_paid/tuition_paid`,
`v_branch_pnl.income_registration_fees`, הנהלת חשבונות). כרטיס התלמידה: דמי
רישום, שכר לימוד, **תשלום X מתוך 10**, אישור התקנון, חודש הניסיון.

**אחרי התשלום**: `rpc_record_sumit_payment` → טריגר → התלמידה **פעילה**.
**ביטול הרשמה** (הבעלים, כרטיס התלמידה): רק בתוך חודש הניסיון (`trial_days`),
זיכוי `cancel_refund` מדמי הרישום כתשלום שלילי (`source='refund'`); אחרי
החודש הכפתור חסום עם הסבר. **רשימת תפוצה** `/mailing` (בעלים): מי שאישרה, עם
ייצוא. **גבייה → "נרשמו ולא שילמו"**: ימים מההרשמה, מעל 3 מסומן, שליחה מחדש.
**הסיכום היומי בוואטסאפ**: "הרשמות היום: נרשמו X, שילמו Y" ו"ממתינות לתשלום
מעל 3 ימים: שמות (ימים)".

בדיקות: `17_enrollment.sql` (מבנה מאומת, דף בטוח, הרשמה, אימות והצפה,
הפעלה, ביטול, סיכום), `enrollment.test.mjs` (אימות זהה בלקוח, אין סכומים
בקוד, הסיכום), 8 בקרות שלילה.

## גבייה בכרטיס — SUMIT (שלב א, שלד מול תשובות מוקלטות)

**הזרימה.** "💳 קישור תשלום" ליד חייבת (גבייה, וכרטיס התלמידה) → `rpc_create_payment_link`
נועל תלמידה וסכום (לא יותר מהיתרה) ברשומה ב-`payment_links`, ומכניס לתור התזכורות
הודעת וואטסאפ עם **הקישור שלנו** `/pay/<טוקן 64 הקס>` → ההורה פותחת, לוחצת
"לתשלום" → `sumit-checkout` יוצר את דף SUMIT **עכשיו**, עם הסכום מהרשומה →
ההורה משלמת, SUMIT מפיקה קבלה → **האישור מגיע רק מ-SUMIT**: `sumit-webhook`
(טריגר של SUMIT, סוד משותף בכותרת `x-webhook-secret`) הוא רמז בלבד, ואחריו
`cron-sumit-sync` (כל שעה) — שניהם שואלים את SUMIT (`getPaymentStatus`) ורק אז
`rpc_record_sumit_payment` רושם תשלום ומעדכן יתרה. החזרה מהדפדפן היא "תודה,
בודקים", לעולם לא אישור.

**ההגנות, ואיפה נבדקות** (`16_payment_links.sql`, `sumit.test.mjs`):
| הגנה | איפה |
|---|---|
| `external_identifier` שלנו על כל תשלום; רישום אידמפוטנטי (payment_id יחיד לקישור, מזהה SUMIT ייחודי) | 0022, `rpc_record_sumit_payment` |
| קישור פג אחרי 7 ימים | `expires_at`, `f_payment_link_alive`, הדף והצ'קאאוט מסרבים |

| תשלום ב-SUMIT שלא נרשם → התראה קריטית; סכום שונה → נרשם מה שנגבה + התראה; תשלום יתום → התראה | `sumit-sync.ts`, RPC |

**מה צריך מהלקוחה:** `SUMIT_COMPANY_ID`, `SUMIT_API_KEY` (קודם של ארגון
בדיקה, "בדיקות" בשם, עם מסוף בדיקה וכרטיסי דמה), מודולים: API, סליקת אשראי,

**להריץ פעם בשבוע, ידנית.** הגיבוי מכיל את כל הטבלאות ב-public ואת
`auth.users` + `auth.identities` — בלעדיהם המשתמשות לא נכנסות אחרי שחזור.
הקובץ מכיל טלפונים, כתובות וכספים: הוא ב-`.gitignore`, ושומרים אותו במקום
מוגן (כונן מוצפן, לא במייל).

**היעד.** שני הסקריפטים משתמשים במה שב-`.env.verify`: `SUPABASE_ACCESS_TOKEN`
(Management API) או `SUPABASE_DB_URL`. `PGURL` מפורש גובר על שניהם — מי
שנתן מחרוזת חיבור התכוון אליה. אם יש `pg_dump` ו-`SUPABASE_DB_URL`, נוצר
בנוסף קובץ `.dump` (שחזור: `pg_restore --clean --no-owner -d "$SUPABASE_DB_URL"`).

**שחזור, צעד אחר צעד:**

1. הסכמה קודם: `./scripts/db-push.sh` על הפרויקט (השחזור מסרב אם גרסת
   המיגרציות ביעד שונה מזו שבגיבוי).
2. `npm run restore -- <קובץ>` בלי `--yes` ומקריאים: מקור, זמן, מספר שורות, יעד.
3. `--yes`. הסקריפט מנקה את היעד, מכניס את רשימת המורשים, ואז את
   `auth.users` — השער יוצר את הפרופילים עם אותם מזהים — ואז את השאר לפי
   סדר המפתחות הזרים. חשבונות שהוסרו מהרשימה עוברים דרך רישום זמני
   שנמחק מיד, ולכן נשארים כבויים כמו במקור.
4. הסקריפט משווה כל טבלה למניפסט ונכשל אם ספירה אחת לא תואמת.
5. המשתמשות נכנסות בגוגל כרגיל; המזהים שלהן לא השתנו.

`backup-roundtrip.test.mjs` עושה את זה בכל ריצה על המסד המקומי: גיבוי,
שיבוש (מחיקת תלמידות ונוכחות, הסרת מורשה, שינוי הגדרה), שחזור, והשוואת
md5 של כל טבלה למקור.

### גיבוי אוטומטי במייל, כל יום ב-22:00

`cron-backup` (Edge Function) רצה מ-pg_cron. מה שהיא עושה, בסדר הזה:

1. `rpc_backup_dump()` — כל המסד מצד המסד, באותו פורמט של `npm run backup`.
2. העלאה ל-Storage (`backups/`), **הורדה בחזרה ואימות**: הקובץ נפרס וכל
   טבלה תואמת למניפסט. "הועלה" אינו "ניתן לשחזור".
3. נשמרים 30 האחרונים; הישנים נמחקים.
4. מייל: הקובץ מצורף מתחת ל-20MB, אחרת קישור חתום ל-7 ימים. בכל מקרה
   העותק ב-Storage.
5. כל כשל → מייל התראה + `alertOwner` (יומן, באנר, webhook). אם גם המייל
   לא יוצא, ההתראה הפנימית נשארת. אין שתיקה.

ה-cron יורה ב-19:00 וב-20:00 UTC (שעון קיץ/חורף), והפונקציה רצה רק
כשבישראל 22:00. הקריאה מוגנת: `Authorization` חייב להיות `CRON_SECRET`, סוד
ש-`backup:schedule` מנפיק, קובע לפונקציה ושומר ב-Vault של הפרויקט.

```bash
npm run backup:schedule        # רישום המשימה ב-pg_cron (פעם אחת)
npm run backup:pull -- 3       # הורדת 3 הגיבויים האחרונים מ-Storage ל-backups/
npm run restore -- backups/<קובץ> --yes
```

`backup-roundtrip.test.mjs` משחזר גם מהקובץ ש-`rpc_backup_dump()` מייצר
ומשווה md5 לכל טבלה — כלומר הקובץ שמגיע במייל וב-Storage מוכח כניתן
לשחזור בכל ריצת CI. `backup-mail.test.mjs` מכסה את ההחלטות: שעה, סף
הצרופה, 30 האחרונים, ואימות הקובץ. שלוש בקרות שלילה.

**סודות** (Edge Functions, דרך `deploy.sh` או הדשבורד): `RESEND_API_KEY`,
`BACKUP_MAIL_TO` (אפשר כמה, מופרדים בפסיק), `BACKUP_MAIL_FROM` (כתובת
בדומיין מאומת ב-Resend).
