# נוהל שחזור מגיבוי — ותרגיל השחזור

גיבוי שלא שוחזר מעולם הוא לא גיבוי. הנוהל הזה רץ **לפני המסירה, ואחרי כל
שינוי במיגרציות או בסקריפטי הגיבוי**, ולפחות פעם ברבעון.

## התרגיל (אוטומטי)

```bash
npm run backup:pull            # הגיבוי האחרון מ-Storage → backups/
npm run restore:drill          # פרויקט ריק → שחזור → אימות שורה-שורה → חבילות ההרשאות
```

מה קורה, ומה נמדד (ריצה מ-2026-09-04, גיבוי אמיתי מהענן: 28 טבלאות, 300 שורות):

| שלב | מה | זמן שנמדד |
|-----|-----|-----------|
| 1 | "פרויקט" ריק: מסד חדש, 18 מיגרציות, אפס נתונים (כמו פרויקט Supabase שנמחק ונבנה עם `db push`) | 1 שנ' |
| 2 | `restore.mjs`: רשימת המורשים → `auth.users` דרך השער → פרופילים → כל השאר לפי מפתחות זרים → הקישורים | 1 שנ' |
| 3 | `restore-verify.mjs`: **כל שורה בכל טבלה** מושווית לגיבוי תו-בתו; ובמפורש: חשבונות auth, זהויות גוגל, קישור רשימה↔פרופיל, תפקידים, שיוכי סניף, טוקני נוכחות (טוקן משוחזר פותח גיליון), הגדרות, גרסת מיגרציות | <1 שנ' |
| 4 | חבילות ההרשאות 02/05/11 על המסד המשוחזר: RLS אוכף, לא רק "קיים" | <1 שנ' |

סה"כ **2 שניות** על הנפח הנוכחי. הזמן גדל ליניארית עם השורות; 500 תלמידות
ו-3,000 תשלומים נמדדו ב-`supabase/tests/14_real_data.sql` (ראה README).

בקרות שלילה (`negative-control.sh`): שחזור שמדלג על טבלה, ואימות שסופר
שורות בלבד (שם תלמידה שונה) — שניהם מפילים את התרגיל.

## שחזור אמיתי לענן — צעד אחר צעד

זמן כולל צפוי: **כ-15 דקות**, רובו המתנה לפרויקט חדש ב-Supabase.

1. **הגיבוי.** `npm run backup:pull -- 3` (שלושת האחרונים מ-Storage; כל
   קובץ אומת בהורדה בחזרה כשנוצר). אם ה-Storage אבד יחד עם הפרויקט:
   הקובץ מהמייל היומי (כשמחובר) או מהכונן המוצפן של `npm run backup`.
2. **פרויקט.** אם הפרויקט קיים ורק הנתונים נפגעו — מדלגים לצעד 4. אחרת
   פרויקט חדש ב-Supabase (אותו אזור, eu-central-1), ~3 דק' עד ACTIVE.
   ב-`.env.verify`: `SUPABASE_PROJECT_REF` החדש.
3. **סכמה.** `./scripts/verify-cloud.sh 1` (כל המיגרציות). לא seed — הגיבוי
   מכיל הכול. השחזור מסרב אם גרסת המיגרציות ביעד שונה מזו שבגיבוי.
4. **שחזור.** `npm run restore -- backups/<קובץ>` (יבש, לקרוא: מקור, זמן,
   שורות, יעד) ואז `--yes`. **מוחק את היעד.** ~10 שנ' דרך ה-Management API.
5. **אימות.** `npm run restore:verify -- backups/<קובץ>` — חייב להיות ירוק.
6. **מה שלא בגיבוי, ונבנה מחדש מהריפו:**
   - Auth: גוגל בלבד (`verify-cloud.sh 3` בודק; ההגדרה ב-`scripts/auth-config.mjs`),
     וב-Google Cloud כתובת ההחזרה של הפרויקט החדש.
   - Edge Functions: `node scripts/functions-deploy-api.mjs` + הסודות
     (`ANTHROPIC_API_KEY`, `META_*`, `RESEND_*`; ראה `supabase/functions/README.md`).
   - הגיבוי היומי: `npm run backup:schedule` (pg_cron + Vault + `CRON_SECRET`).
   - דלי `backups` ב-Storage (פרטי) — `cron-backup` יוצר אותו בריצה הראשונה.
   - Netlify: `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` של הפרויקט
     החדש, ואז `verify-cloud.sh 7`.
7. **סבב האימות המלא** `./scripts/verify-cloud.sh`, ואז כניסה בגוגל של
   הבעלים ובדיקה בעיניים: תלמידות, גבייה, קישור נוכחות שנשלח בעבר עדיין
   עובד (הטוקנים לא השתנו).

## מה לא מכוסה, במפורש

- **קבצים ב-Storage** מלבד הגיבויים (קבלות/חשבוניות, אם יתווספו) — אינם
  בגיבוי. להוסיף לפני שהמערכת מתחילה לשמור קבצים.
- **תרגיל ענן-לענן** (מחיקת פרויקט אמיתי ושחזור לפרויקט חדש) לא רץ
  אוטומטית: דורש פרויקט Supabase שני, והחשבון במכסת החינם (2 פרויקטים
  פעילים). התרגיל האוטומטי משחזר גיבוי אמיתי מהענן למסד ריק בעל אותה
  סכמה ואותן טבלאות auth (ה-shim המקומי נאמן לעמודות של GoTrue בדיוק
  בשביל זה). כשיש פרויקט פנוי — צעדים 2–7 למעלה, ולמדוד.
